# แนวทางลายมือชื่อและหลักฐานอิเล็กทรอนิกส์ของ Valor ERP

> ตรวจทานล่าสุด: 29 ตุลาคม 2569

เอกสารนี้อธิบายรูปแบบที่ระบบนำไปใช้ โดยอิงหลักเกณฑ์ของ ETDA และ พ.ร.บ.ว่าด้วยธุรกรรมทางอิเล็กทรอนิกส์ ไม่ใช่คำรับรองทางกฎหมายเฉพาะคดี ควรให้ฝ่ายกฎหมาย/บัญชีและผู้สอบบัญชีตรวจนโยบายก่อนใช้งานจริง โดยเฉพาะงานจัดซื้อภาครัฐหรือธุรกรรมมูลค่าสูง

## ระดับที่ระบบใช้อยู่

ระบบใช้ **ลายมือชื่ออิเล็กทรอนิกส์ทั่วไป (ประเภทที่ 1)** ผ่านบัญชีผู้ใช้ที่ยืนยันตัวตนและการกรอกรหัสผ่านซ้ำ พร้อมบันทึกเจตนา Revision เวลา IP User-Agent และ SHA-256 ของข้อมูล/ไฟล์หลักฐาน วิธีนี้ออกแบบให้พิสูจน์ผู้ลงนาม เจตนา และความครบถ้วนของข้อมูลได้ แต่ **ไม่ใช่** Digital Signature แบบ PKI และไม่ใช่ใบรับรองจากผู้ให้บริการออกใบรับรอง

ภาพลายเซ็น PNG เป็นเพียงรูปแบบการแสดงผลของเจ้าของบัญชี ไม่ใช่หลักฐานที่เพียงพอด้วยตัวเอง ระบบจึงเก็บ PNG แบบ Version ที่แก้ไขย้อนหลังไม่ได้ คำนวณ SHA-256 และ Snapshot ภาพ Version ที่ใช้ไว้กับการอนุมัติแต่ละครั้ง ภาพใหม่จะใช้กับงานใหม่เท่านั้นและไม่เปลี่ยนเอกสารเก่า

หากนโยบายบริษัท คู่ค้า หรือหน่วยงานรัฐกำหนดให้ใช้ลายมือชื่ออิเล็กทรอนิกส์ที่เชื่อถือได้ประเภท 2–3 ต้องเชื่อมผู้ให้บริการ PKI/e-Signature เพิ่มเติม และควรใช้ MFA ตามระดับความเสี่ยง

## Workflow ที่ถูกนำไปใช้

### 1. บริษัทออกใบเสนอราคาให้โรงพยาบาล

1. Sale สร้างและแก้ไข Draft; ระบบ Autosave Draft ระหว่างแก้ และสร้าง Revision เอกสารเมื่อยืนยันตาม workflow โดยเลขใบเสนอราคาเดิมคงเดิม
2. Super Admin แนบ PNG ลายเซ็นประจำบัญชี ตรวจตัวอย่าง แล้วจึงทำเครื่องหมายว่าได้รับมอบอำนาจลงนาม หลังตรวจอำนาจตามหนังสือรับรองบริษัท/หนังสือมอบอำนาจ
3. Approve ตรวจ Revision ล่าสุด อ่านข้อความแสดงเจตนา ทำเครื่องหมายยืนยัน และกรอกรหัสผ่านบัญชีซ้ำ
4. ระบบสร้างหลักฐานที่แก้ไขย้อนหลังไม่ได้ โดยเก็บผู้ลงนาม บทบาท อีเมล เวลา IP User-Agent ข้อความเจตนา Snapshot SHA-256 ของข้อมูล และ SHA-256 ของภาพลายเซ็น
5. PDF ใบเสนอราคาแสดงภาพลายเซ็น Version ที่ถูกผูกไว้ ผู้อนุมัติ และ hash ของ Revision นั้น
6. Sale ส่งลิงก์ Customer Acceptance Portal ให้ลูกค้า ลูกค้าตรวจ PDF/Revision กรอกชื่อ ตำแหน่ง หน่วยงาน อ่านข้อความแสดงเจตนา แล้ววาดลายเซ็นหรืออัปโหลด PNG
7. ระบบเก็บชื่อ/ตำแหน่ง/หน่วยงาน/อีเมล วิธีลงนาม เจตนา เวลา IP User-Agent ภาพและ SHA-256 ของภาพ พร้อม Snapshot/SHA-256 ของ Revision ที่ลูกค้าเห็นแบบแก้ย้อนหลังไม่ได้
8. ทางเลือกสำรองยังคงรองรับการอัปโหลด PDF ที่ลูกค้าลงชื่อหรือ PO ต้นฉบับ โดยเก็บเป็น Version และไม่เขียนทับไฟล์เก่า กรณี PO ต้องบันทึกเลข PO ของลูกค้าก่อนยืนยัน

### 2. โรงพยาบาลส่ง PO มาโดยตรง

1. Sale เลือกเส้นทาง “มี PO แล้ว — เปิดบิลโดยตรง” และอัปโหลด PO ต้นฉบับ ระบบคำนวณ SHA-256 และเก็บไฟล์แบบ Version; การอัปโหลดใหม่ไม่เขียนทับไฟล์เก่า
2. AI ช่วยอ่านข้อมูลได้ แต่ Sale ต้องตรวจและเป็นผู้ยืนยันข้อมูลที่นำไปใช้
3. ระบบสร้าง `billing_records` โดยตรง ไม่สร้าง `quotations`, ไม่กำหนด `ref_qt_id` และไม่ขอเลข `qt_no`
4. Approve อนุมัติรายการภายใน Valor ERP ด้วยหลักฐานอิเล็กทรอนิกส์แยกต่างหาก
5. ห้ามใส่ลายเซ็น Approve ของบริษัทลงบน PO ต้นฉบับของโรงพยาบาล เพราะผู้อนุมัติเป็นผู้อนุมัติภายใน ไม่ใช่ผู้ออก PO
6. ใช้ “ใบรับรองหลักฐานการอนุมัติอิเล็กทรอนิกส์” ของระบบประกบกับ PO เมื่อต้องตรวจสอบย้อนหลัง

หมายเหตุ: PO Direct เหมาะเมื่อ PO มีข้อมูลที่ใช้ยืนยันคำสั่งซื้อครบและบริษัทไม่จำเป็นต้องเสนอเงื่อนไขใหม่ หาก PO ขาดราคา เงื่อนไข หรือมีรายละเอียดที่ต้องต่อรอง ให้ใช้เส้นทางใบเสนอราคาก่อน ห้ามสร้างใบเสนอราคาย้อนหลังเพียงเพื่อเติมลำดับเอกสาร

## หลักฐานที่ต้องเก็บ

- เอกสารและ Revision ที่ผู้ลงนามเห็นในเวลานั้น
- ข้อความแสดงเจตนาที่ชัดเจน
- ตัวตน บทบาท และอีเมลของผู้ลงนาม
- เวลาแบบมีเขตเวลา IP และ User-Agent
- SHA-256 ของ Snapshot และไฟล์ PO/หลักฐานลูกค้า
- Audit log ของการสร้าง แก้ไข อนุมัติ ดาวน์โหลด และยกเลิก
- Version เก่าของเอกสาร ห้าม hard delete หรือเขียนทับ
- เหตุผลและผู้ดำเนินการ หากต้องเพิกถอนหลักฐาน
